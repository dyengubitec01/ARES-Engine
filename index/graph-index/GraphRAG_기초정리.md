## 1. 큰 그림 — 왜 "그래프"인가?

**일반(벡터) RAG**는 문서를 잘게 쪼갠 **청크(chunk)** 를 벡터로 만들어, 질문과 **의미가 비슷한** 청크를 찾아온다. "비슷한 덩어리 검색."

약점: **"A와 B가 무슨 관계지?"**, **"이 주제에 관련된 것들 다 뭐야?"** 같은 질문은 답이 여러 청크에 흩어져 있어 벡터 검색이 약하다.

**그래프RAG**는 문서에서 **"누가/무엇이 등장하고, 서로 어떻게 연결돼 있는지"** 를 미리 뽑아 **지도(그래프)** 로 만들어 둔다. 그래서 "연결 관계"를 따라가는 질문에 강하다.

---

## 2. 그래프(Graph)란 — 점과 선

여기서 "그래프"는 막대그래프가 아니라 **점들과 그 점을 잇는 선들의 모음**이다.

```
   [김철수] ───근무─── [A회사]
      │                  │
    참여               포함
      │                  │
   [프로젝트X] ──사용── [GPU서버]
```

- **점 = 노드(node)** 또는 **버텍스(vertex)**
- **선 = 엣지(edge)**

그래프 = 노드 집합 + 엣지 집합. 이게 전부다.

---

## 3. 엔티티 (Entity) = 노드

**엔티티** = 문서에 등장하는 **의미 있는 대상**(주로 고유명사·핵심 개념).

- 사람 `김철수`, 조직 `KT클라우드`, 제품/기술 `GPU서버`·`BGE-M3`, 장소·개념 등

문서에서 이런 엔티티를 뽑는 걸 **엔티티 추출(entity extraction)** 또는 **NER(Named Entity Recognition, 개체명 인식)** 이라 한다. 우리 파이프라인은 `GLiNER2` 모델이 담당(LLM 아님, 로컬 NER 모델).

> **엔티티 = 노드(점)**

---

## 4. 관계 (Relation) = 엣지 & 관계 라벨

**관계** = 두 엔티티가 어떻게 연결되는지. 그래프의 **엣지(선)**.

```
[김철수] ──(근무한다)──> [KT클라우드]
```

셋으로 표현하면 **(김철수, 근무한다, KT클라우드)** → 이런 `(주어, 관계, 목적어)` 묶음을 **트리플(triple)** 이라 한다.

- **엣지(edge)** = 두 노드를 잇는 선 (연결됐다는 사실)
- **관계 라벨(relation label)** = 그 선에 붙은 이름 (`근무`/`포함`/`사용`…)

우리 시스템은 per-chunk LLM(gemma-4-31b)이 청크를 읽고 엣지에 관계 라벨을 붙인다. **현재 라벨 커버리지는 약 18%** — 나머지 82%는 이름 없는 공출현 엣지다(뒤 히스토리 참고).

---

## 5. 공출현 (Co-occurrence) — 가장 약한 관계

`co(함께) + occurrence(등장)` = **같이 나타남**.

> 두 엔티티가 **같은 청크에 함께 등장**하면 "관련 있겠지"라고 보고 엣지를 긋는 것.

```
청크: "김철수는 프로젝트X에서 GPU서버를 세팅했다."
  → 김철수–프로젝트X, 김철수–GPU서버, 프로젝트X–GPU서버 엣지 생성
```

**중요**: 공출현은 관계의 **"이름"을 모른다.** 그냥 "같이 나왔으니 연결됨"만 안다.
- 공출현 엣지 = "관계가 **있다**"만 아는 약한 엣지
- 관계 라벨링 = 거기에 "근무한다/포함한다" 같은 **구체적 의미**를 붙이는 강화 작업

> 원칙: **잘못된 관계 < 관계 없음 < 정확한 관계**

---

## 6. 가중치 (Weight) — 관계의 세기

엣지에 붙는 숫자. 우리 시스템은 **공출현한 청크 수**를 가중치로 쓴다.

- 30개 청크에 같이 등장 → weight 30 (강한 연결)
- 1개에만 → weight 1 (약한 연결)

> ⚠️ 이 "raw 공출현 횟수" 방식이 hairball의 원인 중 하나다. 13번 PMI에서 대안을 다룬다.

---

## 7. 관계 라벨 vs 커뮤니티 — 헷갈리는 포인트

둘 다 그래프 구조지만 **완전히 다른 층위**다.

> **관계 라벨 = 두 엔티티 "사이의 선"에 붙은 이름 (1:1)**
> **커뮤니티 = 여러 엔티티가 뭉친 "그룹" (다수)**

```
        [스마트도시]
        /    |    \
  포함/   협력|     \사용        ← 관계 라벨 (엣지 하나하나에 붙은 이름)
    /        |       \
[CCTV]───[관제센터]───[AI]
    ┗━━━━━━━━━━━━━━━━━━━┛
         커뮤니티 A            ← 커뮤니티 (이 노드들이 한 무리)
```

| | 관계 라벨 | 커뮤니티 |
|---|---|---|
| **규모** | 엔티티 2개 (선 1개) | 엔티티 수십~수만 개 (무리) |
| **말해주는 것** | 둘이 **어떻게** 연결되나 | 무엇들이 **같은 편**인가 |
| **답하는 질문** | "A와 B **관계**가 뭐야?" (좁음) | "이 **주제** 관련 다 뭐야?" (넓음) |
| **만드는 법** | LLM이 청크 읽고 이름 붙임 | Louvain이 연결 밀도로 자동 탐지 |

**비유(SNS 친구 관계):**
- 관계 라벨 = "철수와 영희는 **부부**다" (두 사람 사이의 구체적 관계)
- 커뮤니티 = "철수가 속한 **등산 동호회 30명**" (무리 전체)

> 부부 관계(라벨)를 아무리 모아도 그게 동호회(커뮤니티)가 되는 건 아니다. **줌인(선 하나) vs 줌아웃(뭉텅이).**

---

## 8. 커뮤니티 — 어떤 기준으로 만들어지나 (심화)

가장 헷갈리는 부분. **커뮤니티는 "의미"로 묶는 게 아니다.** 오직 **"누가 누구랑 연결됐나(선의 패턴)"** 만 보고 묶는다.

### 커뮤니티 형성이 보지 않는 것 / 보는 것

| ❌ 안 봄 | ✅ 봄 |
|---|---|
| LLM 콜 (0회) | 선의 목록 (누가 누구랑 이어졌나) |
| 유사도/임베딩(벡터) | 가중치 (공출현 횟수) |
| 엔티티의 의미 (CCTV가 뭔지) | |
| 관계 라벨 (`협력`인지 `포함`인지) | |

→ 입력은 **단 하나: "엣지 목록 + 가중치"** 뿐. 그 외 정보는 아예 안 들어간다.

### 기준 = "안은 빽빽, 밖은 듬성"

> **어떤 노드들에 경계선을 그었을 때, 그 안에 선이 많이 남고(内) 경계를 넘는 선은 적으면(外) → 좋은 커뮤니티.**

**숫자로 세어보기.** 노드 6개, 선: `A-B, A-C, B-C`(왼쪽) / `D-E, D-F, E-F`(오른쪽) / `C-D`(다리):

```
   A───B          D───E
   │ ╲ │          │ ╲ │
   └─ C ───────── D ─┘ F
```

- **후보 1** {A,B,C}+{D,E,F}: 안의 선 6개, 넘는 선 1개(C-D) → **아주 좋음** ✅
- **후보 2** {A,B,D}+{C,E,F}: 안의 선 2개, 넘는 선 5개 → **엉망** ❌

알고리즘은 이런 경계를 수없이 시도해 **"안 최대, 밖 최소"인 나눔**을 찾는다.

### "빽빽"은 무엇으로 정해지나 — 연결 개수 × weight

위 예시는 **선의 개수**만 셌지만, 실제 "빽빽함"은 **두 재료의 곱**이다:

```
빽빽함 = (연결 개수) × (각 연결의 weight)
          └ 엣지 몇 개냐     └ 각 엣지가 얼마나 강한가(공출현 횟수)
```

- **연결 개수** = 그룹 안 엔티티들이 **엣지 몇 개로 이어졌나** (공출현 쌍 수)
- **weight** = 그 엣지 각각의 **세기**

> ⚠️ **"연결 개수" = 엣지(공출현 연결선) 개수 ≠ 관계 라벨(18%) 개수.**
> 엣지는 공출현하면 생기고(라벨 없어도), 커뮤니티 형성은 **엣지 전부**(예: 89만 개)를 보지 라벨 붙은 것(18만)만 보는 게 아니다.

| | 정체 | 커뮤니티 형성에 쓰임? |
|---|---|---|
| **엣지(연결)** | "같은 청크에 나옴" 선 | ✅ 개수·weight 둘 다 |
| **관계 라벨** | 그 선에 LLM이 붙인 이름(`포함`…) | ❌ 아예 안 들어감 (6·7번) |

### weight = "묶이냐 빠지냐"가 아니라 "어느 그룹이냐(경계)"

흔한 오해: *"weight 낮으면 커뮤니티에서 빠지고, 높으면 들어간다."* → **아니다.**

- **모든 엔티티는 *어딘가* 커뮤니티에 속한다** (연결이 0이면 혼자 = 싱글톤).
- weight는 "묶이냐/빠지냐"가 아니라 **"어느 그룹에 묶이냐 = 경계를 어디 긋냐"** 를 정한다.

**친구 그룹 비유** (weight = 친분 세기):
- **강한 친분(high weight)** → 같은 그룹으로 **끌려감**
- **약한 친분(low weight)** → 다른 그룹에 있어도 됨 (억지로 안 당김)

**두 덩어리가 합쳐지냐 갈라지냐:**
```
교통 ═══ 신호등 ═══ 도로      [교통 그룹]
         ┊ (2, 약함)          ← weight 낮음 → 안 당김 → 갈라진 채 유지
수질 ═══ 정수장                [수질 그룹]
```
- 교통↔수질 weight **낮음** → 서로 안 당겨 → **각자 그룹** (2개 유지)
- 교통↔수질 weight **높음**(자주 겹침) → 당겨서 → **한 그룹으로 합침**

> **low weight = 커뮤니티 밖 ❌.** weight는 그룹 *경계*를 정하는 **당김의 세기**. 강하면 뭉치고 약하면 갈라져도 됨. **연결이 아예 없을 때만** 혼자(싱글톤)가 된다.
> → 우리 그래프의 **99.6% 싱글톤**은 low weight 탓이 아니라 **1청크만 등장해 엣지가 가지치기로 잘려 연결이 0**이 된 것.

이게 **hairball·PMI와 직결**된다: 허브(AI)가 모든 그룹에 **강한 엣지** → 다 당겨 한 덩어리(hairball). PMI가 허브 weight를 깎으면 → 그룹 밖 당김이 약해져 → 진짜 주제끼리 갈라진다. (13번 PMI)

### 왜 "주제 그룹"처럼 보이나

관련 있는 것들끼리 자연히 자주 같이 등장(=연결)되니까, **연결 패턴만 세도 주제 그룹이 저절로 딸려 나온다.** 주제로 묶은 게 아니라, **연결로 묶었더니 주제가 따라온** 것.

### 모듈성(Modularity, Q) — 허브 보정

현실엔 `CCTV`처럼 **모두와 연결된 허브**가 있다. 허브는 우연히도 어느 그룹과든 선이 많아서, 단순히 "안의 선 개수"만 세면 허브가 다 이겨버린다. 그래서 진짜 기준(**모듈성 Q**)은:

> **Q = (실제로 안에 있는 선) − (노드 연결 수를 감안해 우연히도 안에 생겼을 선)**

즉 **"우연히 기대되는 것보다 *더* 뭉쳤나"** 를 본다. 이게 허브가 커뮤니티를 조작하는 걸 막는 장치다.

### Louvain(루뱅) 알고리즘

Q를 최대화하는 **욕심쟁이(greedy) 휴리스틱**. 두 단계 반복:
1. **지역 최적화**: 모든 노드가 각자 그룹 → "Q가 가장 오르는 이웃 그룹"으로 이사 → 안정될 때까지
2. **압축**: 만들어진 그룹을 노드 하나로 합쳐 작은 그래프 생성 → 다시 1단계

계층적(hierarchical)이라 작은 커뮤니티 → 큰 커뮤니티. `resolution` 파라미터로 크기 조절(높이면 잘게, 낮추면 크게).

> ⚠️ Louvain의 `resolution`(그룹 크기 조절) ≠ 우리 코드의 "엔티티 resolution/alias"(이름 병합). **완전히 다른 단어.**

## 9. 커뮤니티 요약 — LLM이 무엇을 보나

**형성**(그룹 나누기)엔 LLM이 안 들어가지만, **요약**(그룹에 설명 붙이기)엔 LLM을 쓴다. 이 둘은 별개 단계.

LLM에 넣는 재료는 딱 2개 ([summarize_graph.py](scripts/graph_build/summarize_graph.py)):

1. **엔티티 이름 목록** — 멤버 중 **등장 많은 순 상위 12개만** (`LIMIT 12`)
2. **원본 청크 텍스트 발췌 3개** — 그 엔티티들이 실제 등장한 문서 원문 조각, 각 **300자로 잘라서** (`LIMIT 3`)

프롬프트:
```
다음 엔티티들과 문서 발췌가 한 그룹으로 묶였어. 이 그룹의 공통 주제를 한 문장으로 요약해줘.
엔티티: 스마트도시, CCTV, 관제센터, AI, ...
발췌: (문서 원문 조각 3개)
```

| LLM이 보는 것 | 사용? |
|---|---|
| 엔티티 이름 목록 (상위 12개) | ✅ |
| 원본 문서 발췌 (청크 3개 × 300자) | ✅ |
| 관계 라벨 | ❌ |
| 커뮤니티가 왜 이렇게 묶였는지(연결 패턴) | ❌ |

**핵심 & 한계:**
- 커뮤니티에 엔티티가 수천 개여도 LLM은 **이름 12개 + 청크 3개**라는 **작은 샘플**만 본다 (전부 넣으면 컨텍스트·비용 폭발).
- 그래서 커뮤니티가 **hairball처럼 거대·잡다하면** 이 샘플이 전체를 대표 못 해 → **요약이 부실**해진다.
- 즉 **요약 품질은 "커뮤니티가 애초에 깔끔하게 나뉘었나"에 의존.** hairball 해결(PMI 등)이 커뮤니티 요약보다 먼저인 이유.
- 관계 요약(relation_summary)도 마찬가지로 **두 엔티티가 같이 등장한 청크 원문**을 근거로 요약한다. 둘 다 "원본 텍스트 기반".

## 10. 엔티티-IDF 라우팅 vs 벡터 검색

우리 시스템에서 그래프 검색의 **실질적 핵심 레버**는 화려한 구조가 아니라 **엔티티-IDF 라우팅**이었다(실측 결론, 14번 참고).

| | 벡터 RAG | 엔티티-IDF 라우팅 |
|---|---|---|
| 닮음 기준 | **의미(뜻)** 전체 | **희귀 엔티티 일치** |
| 강점 | 말 바꿔도 잡음, 광범위 | 콕 집은 고유명사 정확 회수 |
| 약점 | 특정 단어가 희석됨 | 의미만 같고 단어 다르면 못 잡음 |

- **IDF(역문서빈도)** = "흔한 엔티티는 점수 낮게, 희귀한 엔티티는 높게."
  `CCTV`처럼 어디나 나오는 건 변별력 0, `ABC-2000`처럼 드문 건 강한 신호.
- **왜 중요?** 실제 질문엔 엔티티가 여러 개 섞인다. IDF 없이 다 똑같이 취급하면 **흔한 엔티티가 후보를 노이즈로 채워** 정작 답이 묻힌다. IDF가 **노이즈 엔티티를 죽이고 변별 엔티티로 조준**한다.
- 효과: 엔티티 종합 질문에서 벡터 대비 회수 **2배(0.53 vs 0.28)**, 벡터와 **직교(상보)** → union하면 순이득.

> 비유: **벡터 = 의미 검색, 엔티티-IDF = 똑똑한 키워드 검색(희귀어 우선).** 옛 TF-IDF를 단어가 아니라 **추출된 엔티티 단위**로 하는 것.
>
> ⚠️ 둘은 상보적이라 **한쪽으로 다른 쪽을 정리(rerank)하면 상보성이 깨져 손해**(vector-rerank −0.074 악화). 독립 union이 운영점.

## 11. 관계성 질문은 어떻게 대응하나

| 유형 | 대응 |
|---|---|
| A·B가 **한 청크/문서에 같이** 설명됨 | ✅ 공출현 청크 회수 + **관계 라벨 엣지**로 대응 |
| A·C가 **여러 단계 건너야** 연결됨 (multi-hop) | ❌ 아직 미구현 — 그래프 순회(traversal) 필요, 후순위 |

- **엔티티-IDF 라우팅**은 "관계 해결책"이 아니라 "어떤 청크를 끌어올지 정하는 **랭킹**"일 뿐.
- 관계 자체에 답하는 건 **그래프의 엣지/관계 라벨**이 한다.
- **multi-hop**(A→B→C, 한 청크에 A·C가 같이 안 나오는 경우)은 엣지를 여러 번 건너야 해서 미구현. 검색측 후순위 레버.

## 12. 인덱싱축 vs 검색축

"관계 답변·global·multi-hop"은 **기능 이름**이고, 각 기능은 **인덱싱축 절반 + 검색축 절반**으로 나뉜다.

- **인덱싱축** = 그래프에 **재료를 깔아두기** (엔티티/엣지/라벨/커뮤니티 생성·저장) — **내 담당**
- **검색축** = 질문 들어오면 그 재료를 **꺼내 쓰기** (순회·라우팅·LLM 답변) — 협업 개발자

| 기능 | 인덱싱축 (재료) | 검색축 (사용) |
|---|---|---|
| 관계 답변 | 엣지에 관계 라벨 붙이기 | 라벨 꺼내 답에 주입 |
| global | 커뮤니티 탐지 + 요약 생성 | 넓은 질문에 요약 라우팅 |
| multi-hop | 엣지 정합성(경로 안 끊기게) | 질문 시 그래프 순회 |

## 13. PMI — 엣지 가중치 고도화 (Tier 1 핵심)

**PMI = Pointwise Mutual Information (점별 상호정보량).** 엣지 가중치를 계산하는 **새로운 방식**.

### 지금 방식의 문제 (raw 공출현)

현재 가중치 = **같이 등장한 청크 수(raw)**. `CCTV` 같은 허브는 **모든 것과** 자주 나오니 허브 엣지가 다 강해짐 → **hairball**.

### PMI가 하는 일

> **PMI ∝ 같이_나온_횟수 ÷ (a의 빈도 × b의 빈도)**

"같이 나온 횟수"를 **각자 빈도로 나눠 보정** → "흔해서 우연히 같이 나왔나 vs 정말 특별히 붙어다니나" 구분.

### 숫자 예시

**쌍 1: CCTV ↔ 관제센터** (CCTV 1만 청크, 관제센터 5천, 같이 3천)
- raw = **3000** (큼!) — 근데 둘 다 흔해서 당연
- PMI = 3000 ÷ (10000 × 5000) = **아주 작음** ↓

**쌍 2: ABC-2000 ↔ 방수패널** (각 5·4 청크, 같이 4)
- raw = **4** (작아서 지금은 무시됨) — 근데 거의 항상 같이!
- PMI = 4 ÷ (5 × 4) = **0.2 → 훨씬 큼** ↑

→ **raw는 "CCTV 쌍이 강함"이라지만 PMI는 "ABC-2000 쌍이 진짜 의미 있음"으로 뒤집는다.**

### 왜 유망한가

| | 효과 |
|---|---|
| **hairball 정조준** | 허브 엣지 가중치를 깎아 → 뭉친 게 풀릴 가능성 |
| **증명된 원리의 확장** | **IDF(흔한 엔티티 죽이기)의 엣지-레벨 쌍둥이** |
| **매우 쌈** | LLM·벡터 0, 가중치 계산식만 교체 ([build_graph.py:290-297](scripts/graph_build/build_graph.py#L290-L297)) |

> 성공하면 커뮤니티가 살아나고(global 가능), 엣지가 정제되고(multi-hop 경로 신뢰↑) → 세 미래 능력의 토대가 한 번에 개선. **인덱싱측 첫 실험 후보.**

## 14. 측정 히스토리 — 우리가 실측으로 배운 것

**결론부터: 인덱싱측 recall(회수)은 이미 천장 도달.** 여러 기법을 골든셋(recall@10)으로 측정한 결과:

| 시도한 것 | 측정 결과 | 판정 |
|---|---|---|
| 엔티티 resolution(alias) | Δ +0.006 (노이즈 수준) | ≈0, retrieval 레버 아님 |
| 큐레이션 | 0.000 | 무효 |
| NER 폴백 | +0.005 | 미미 |
| 커뮤니티 라우팅 | 광범위 노이즈 | **기본 off** |
| **vector-rerank** | **−0.074** | **악화(금지)** |
| 관계-Louvain(관계가중 커뮤니티) | hairball 안 깨짐 | **기각** |
| **엔티티-IDF 라우팅** | 벡터 2배(0.53 vs 0.28), +0.19 union | ✅ **유일한 유의미 레버** |

**핵심 통찰:**
- 그래프의 가치는 **후보집합 확장도, 커뮤니티도 아니고, "벡터와 직교하는 랭킹(엔티티-IDF)" 그 자체.**
- 그래서 정리/rerank로 "개선"하려 하면 **벡터와의 상보성이 깨져 손해.** +0.19 union이 운영점.
- **hairball = 허브(hub) 문제** — 고degree 엔티티(CCTV/AI/스마트도시)가 공출현·라벨·관계 어디에나 끼는 도메인 구조 문제. **관계 가중치로는 안 깨짐**(그래서 관계-Louvain 기각).
- resolution 결정: **명시 alias 11쌍만 유지, cosine 자동병합 폐기**(retrieval 가치 ≈0 + 자기규칙 망각 퇴화버그).

**즉 "그래프로 recall을 더 짜낸다"는 방향은 닫혔고**, 진짜 남은 금맥은 **다른 축**(관계 답변·global·multi-hop) = 아래 Tier들.

## 15. 인덱싱측 고도화 재료 — Tier 1/2/3

recall 축은 천장이지만, **관계답변·global·multi-hop용 재료**는 비어있거나 거칠어서 더 깔 수 있다. recall이 아니라 **다른 축**을 여는 작업.

### 🎯 Tier 1 — 엣지 가중치를 PMI로 (최우선)

- **무엇**: raw 공출현 횟수 → PMI(빈도 보정)로 엣지 가중치 교체 (13번 참고)
- **왜 최우선**:
  - hairball **근본 원인(허브) 정조준**
  - 유일하게 증명된 원리(IDF)의 **구조적 확장** — 이론이 깔끔
  - **가장 쌈**(LLM·벡터 0, 계산식 한 군데)
  - 성공 시 커뮤니티·multi-hop 토대까지 **연쇄 개선**
- **측정**: 빌드 후 커뮤니티 크기 분포 before/after 비교(거대군집이 깨지나)
- **코드**: [build_graph.py:290-297](scripts/graph_build/build_graph.py#L290-L297) 한 군데. 실험 플래그(`--edge-weight pmi`)로 붙일 수 있음

### Tier 2 — 능력별 토대 (PMI 성공 시 연쇄)

**2-① 커뮤니티 요약 생성** (global용)
- 현재 `summary=NULL`이라 global 능력의 재료가 0
- hairball 상태에선 요약해도 무의미 → **PMI로 커뮤니티가 살아난 다음** top-N 커뮤니티만 LLM 요약
- 순서 중요: Tier 1 → 그 다음 이것

**2-② 엔티티 설명(description) 생성** (관계답변·생성 grounding용)
- Microsoft GraphRAG 핵심 자산인데 우리는 LLM-free라 뺐음(name+type만)
- 22만 전부는 비현실적 → **고-IDF/고-degree 핵심 엔티티 top-N만** 설명 생성
- 비용 중간

**2-③ 관계 라벨 커버리지 18% → 상향** (관계답변용)
- 82%가 맨 공출현(라벨 없음)
- 다 라벨링은 비싸니 **고-weight(또는 고-PMI) 엣지 우선** 라벨링이 비용 대비 효율
- extract_relations 이미 있으니 대상 선정만 바꾸면 됨

### Tier 3 — 정제 (있으면 좋음)

- **엔티티 confidence 필터** — GLiNER2 서버가 score 노출하면 노이즈 엔티티 컷 → 그래프 정밀도↑
- **관계 방향성/타입 세분화** — multi-hop 경로 품질용 (단, "잘못된 관계 < 관계 없음" 원칙 주의)
- **엔티티 타입 세분화** — 현재 equipment→PRODUCT로 뭉개짐 등

### ❌ 하지 말 것 (이미 닫힘)

- resolution 확장 (실측 ≈0)
- 문서-레벨 공출현 (hairball **악화**)
- recall 목적 튜닝 (천장 확정)
- vector-rerank (−0.074 악화)

## 16. 용어 사전

| 용어 | 뜻 |
|---|---|
| **Node / Vertex** | 점 = 엔티티 |
| **Edge** | 선 = 관계/연결 |
| **Triple** | (주어, 관계, 목적어) 3묶음 |
| **NER** | 개체명 인식 = 엔티티 추출 |
| **Co-occurrence** | 공출현 = 같이 등장 |
| **Weight** | 가중치 = 관계 세기 |
| **Community** | 커뮤니티 = 밀집 연결 그룹 |
| **Modularity (Q)** | 모듈성 = 커뮤니티 분할이 얼마나 좋은지 점수 |
| **Louvain / Leiden** | 커뮤니티 탐지 알고리즘 |
| **Resolution** | (Louvain) 커뮤니티 크기 조절 손잡이 |
| **IDF** | 역문서빈도 = 희귀할수록 높은 가중치 |
| **PMI** | 점별 상호정보량 = 빈도 보정한 결속력(허브 억제) |
| **Routing** | 라우팅 = 질문을 관련 엔티티/청크로 보내기 |
| **Orphan** | 고아 = 어디에도 안 연결된/라벨 없는 외톨이 |
| **Hairball** | 털뭉치 = 너무 빽빽해 구분 안 되는 나쁜 그래프 상태 |
| **Hub** | 허브 = 연결(degree)이 매우 많은 노드 (hairball 원인) |
| **Degree** | 차수 = 한 노드에 붙은 엣지 수 |
| **Entity Resolution / Alias** | 엔티티 정규화 = `KT클라우드`=`KT Cloud`를 하나로 병합 |
| **Canonical** | 정규형 = 여러 변형 중 대표 이름 |
| **Multi-hop** | 다단계 추론 = A→B→C로 엣지 여러 번 건너기 |
| **Fan-out** | 한 노드에서 여러 노드로 퍼지는 넓은 질문 |
| **Global query** | 전역 질문 = 코퍼스 전체를 종합해야 답하는 넓은 질문 |
| **Subgraph** | 부분그래프 = 전체 중 질문 관련 일부만 |
| **Rerank** | 재순위 = 후보를 다른 신호로 다시 정렬 (우리 벡터-rerank는 악화) |
| **Recall@K** | 상위 K개 안에 정답이 들어온 비율 (회수 성능 지표) |

## 17. 부록 — 우리 시스템(스마트시티) 현재 상황

- **커뮤니티는 정상 생성·저장**되지만 `CCTV·AI·스마트도시` 허브가 그래프를 다 이어붙여 **hairball**. Louvain이 깔끔하게 못 나눔. 관계 가중으로도 안 깨짐(허브 = 도메인 구조 문제).
- **검색에선 커뮤니티 기본 off**, 진짜 효용은 **엔티티-IDF 라우팅**.
- **커뮤니티 요약은 현재 비어있음**(summary=NULL) → global 능력 재료 없음.
- **관계 라벨 커버리지 ~18%** (82% 맨 공출현).
- **엔티티 = name+type만** (설명 없음).
- **인덱싱측 recall = 천장 도달** — 더 짤 레버 없음.
- **남은 방향** = Tier 1(PMI) → Tier 2(커뮤니티 요약·엔티티 설명·라벨 커버리지) → Tier 3(정제). 검색측(multi-hop·LLM-rerank)은 협업 개발자 영역·후순위.
